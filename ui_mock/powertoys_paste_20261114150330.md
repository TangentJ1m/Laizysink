## System-Wide State & Cross-Screen Contracts

Laizysink operates as a prompt-first mobile browser where `WebView` instances execute silently in the background (`alpha = 0f` or off-screen state) while a backend orchestrator executes a parallel Directed Acyclic Graph (DAG) of tasks via Exa and Gemini. Every screen in the application is a reactive projection of four shared client-side stores:

1. **Task & DAG State Store (WebSocket-Synced):** Maintains active and historical task graphs, mapping internal backend nodes (`DECOMPOSE`, `EXA_SEARCH`, `DATA_BARRIER`, `MERGE`, `HITL_BROWSER`, `KEYCHAIN_REF`) to simplified frontend states.


2. **Background WebView Pool:** Manages headless/hidden Android `WebView` tabs executing automated DOM navigation, form staging, and JavaScript injection. Only one `WebView` may enter the foreground at a time when a Human-in-the-Loop (HITL) barrier triggers.


3. **Temporal Memory Store:** Indexes completed subgraphs and verified user facts across a temporal sliding window (`event_start_date`, `event_end_date`, `created_at`) with freshness tags (`USED`, `STALE_QUERIED`, `ENTIRELY_STALE`).


4. **Zero-Trust Keychain Vault:** Local hardware-backed storage (`Android Keystore` / `EncryptedSharedPreferences`). Raw credentials never leave the device or enter LLM prompts; graph nodes store only opaque pointers (e.g., `vault://jal.co.jp`).

## 1. Laizysink Home

### Role in the System

**Laizysink Home** is the post-tab entry point of the browser. Its role is to capture user intent with minimal friction, surface immediate high-priority background tasks, and keep browser tabs invisible until human intervention is strictly necessary.

### Data Inputs & State Subscriptions

* **Background Tab Counter:** Subscribes to the `Background WebView Pool` to display the real-time count of hidden active sandboxes (e.g., `Tabs Hidden • 2 Active`).


* **Top-2 Task Preview Feed:** Queries the `Task & DAG State Store` for the two highest-priority tasks, ranked by: (1) `BLOCKED_USER` / `Needs Attention`, (2) `RUNNING`, and (3) most recently `COMPLETED`.


* **Temporal Context Indicator:** Subscribes to active sliding-window memory sessions (e.g., an upcoming trip) so newly submitted prompts automatically inherit relevant timeframe and location context.



### Functional Mechanics

* **Prompt Ingestion Pipeline:** Submitting text in the bottom input bar dispatches a `CREATE_TASK` payload containing the raw prompt, attached local file URIs (if added via the attachment icon), and active temporal memory IDs. Immediately upon submission, the client navigates to **Active Task** while the backend begins DAG decomposition.


* **Voice-to-DAG Execution (Gemini Transcribe):** Holding or tapping the microphone control streams audio to Gemini Transcribe. Once transcribed, the text populates the prompt field (or auto-submits on silence detection) so hands-free queries launch parallel branches directly.


* **Quick-Action Starter Chips:** Tapping a preset chip (e.g., `Research cheap flights`, `Summarize open articles`, `Track package delivery`) either pre-fills the prompt bar with structured scaffolding or triggers immediate execution if sufficient context already exists in the `Temporal Memory Store`.


* **Hidden-Tab Status Pill:** Tapping the top-right `Tabs Hidden` indicator does not dump the user into a traditional tab grid; instead, it routes to **All Tasks Hub** filtered to tasks currently holding open background `WebView` sessions.


* **Task Card Routing:** Tapping a preview card inspects its `status`: `BLOCKED_USER` and `RUNNING` tasks route to **Active Task**, whereas `COMPLETED` tasks route directly to **Completed Task Page**.

## 2. All Tasks Hub

### Role in the System

**All Tasks Hub** (accessed via `Review all` on Home) is the global triage center and memory controller. It prevents parallel background tasks from getting lost when multiple requests run concurrently and gives the user explicit visibility into what cross-task context is currently active.

### Data Inputs & State Subscriptions

* **Partitioned Task Lists:** Subscribes to all user tasks in the `Task & DAG State Store`, grouped into three mutually exclusive buckets ordered by most recent state change:
1. `Needs Attention`: Tasks containing at least one node in `BLOCKED_USER` or `HITL_BROWSER` state.


2. `Working in Background`: Tasks with active `RUNNING` branches and zero unresolved user blockers.


3. `Finished`: Tasks where the root `MERGE` node has reached `COMPLETED`.




* **Active Temporal Window Banner:** Reads the `Temporal Memory Store` to display currently active event anchors (e.g., `Japan Trip (Nov 18–23)`) and the count of shared facts available to new prompts.



### Functional Mechanics

* **Priority Triage & Deep-Linking:**
* Tapping a `Needs Attention` card routes directly to the exact blocking interaction—opening **Active Task** scrolled to the active Data Barrier card, or jumping straight to **Keychain Login & Spotlight** if a hidden tab is paused on authentication or checkout.


* Tapping a `Working in Background` card opens **Active Task** so the user can watch live Exa research progress or switch to **Spatial Execution Map**.


* Tapping a `Finished` card opens **Completed Task Page**.




* **Temporal Context Management:** Tapping `Manage` on the top context banner opens a management sheet listing stored facts from recent subgraphs alongside their freshness tags (`USED`, `STALE_QUERIED`, `ENTIRELY_STALE`). Users can manually expire an active context window (forcing future prompts to ignore it) or trigger a manual refresh on stale items.


* **New Task Creation:** Tapping `+ New` returns to **Laizysink Home** with the prompt bar focused.

## 3. Active Task

### Role in the System

**Active Task** is the primary human-facing workspace for an in-progress goal. It intentionally hides the backend's complex multi-branch tree behind a linear stepper and focuses user attention on two things: resolving **Dynamic Data Barriers** and verifying live **Exa Research** snippets.

### Data Inputs & State Subscriptions

* **Linearized Progress Stepper:** Subscribes to aggregate milestone states derived from the backend DAG (e.g., `Plan` $\rightarrow$ `Researching Paths` $\rightarrow$ `Needs Input` $\rightarrow$ `Compare & Book`).


* **Active Barrier Queue:** Listens for `DATA_BARRIER` events emitted over WebSocket when one or more parallel branches stall due to missing parameters (dates, budget, preferences, passenger count).


* **Live Exa Citation Stream:** Subscribes to `EXA_SEARCH` node outputs, displaying total verified source count, top highlighted quote, source domain/favicon, and which background sandbox tab retrieved it.


* **Sandbox Telemetry Footer:** Reflects the exact state of hidden `WebView` instances tied to this `task_id` (e.g., `1 tab paused awaiting input`).



### Functional Mechanics

* **Dynamic Data Barrier Resolution:**
* When a branch hits a missing-information barrier, the center card renders a structured multiple-choice prompt generated from Exa's initial search findings (e.g., realistic price/date tiers) plus an `"Other"` option supporting free-text or Gemini Transcribe voice input.


* Submitting an answer dispatches a `RESOLVE_BARRIER` event. The backend writes the answer to the `Temporal Memory Store` and immediately unblocks *all* parallel branches waiting on those variables simultaneously (e.g., answering dates and budget unblocks both `Find Flights` and `Accommodation` at once).




* **Source Verification & Comparison:**
* Tapping `View All` on the `Live Exa Research` card opens a modal sheet listing all retrieved sources grouped by **Selected / Leading Candidates** versus **Considered & Discarded**, complete with Exa highlighted text excerpts and one-line rejection reasons.




* **View Mode Switching (`Simple` $\leftrightarrow$ `Map`):**
* Tapping the top-right tab/map control transitions to **Spatial Execution Map**, preserving the current `task_id` so the user can inspect the underlying parallel branches and work-tasks.




* **Automatic Escalation to Foreground Browser:**
* If a running branch encounters a login wall, CAPTCHA, or mandatory human confirmation inside its hidden `WebView`, the screen automatically transitions to **Keychain Login & Spotlight** without requiring manual tab hunting.

## 4. Spatial Execution Map

### Role in the System

**Spatial Execution Map** exposes Laizysink's dual-layer execution graph in an inspectable, non-overwhelming way. It separates high-level **Subtask Nodes** (independent parallel tracks such as `Find Flights`, `Accommodation`, `Local Transit`) from granular **Work-Tasks** (individual `EXA_SEARCH`, `DATA_BARRIER`, and `KEYCHAIN_REF` operations attached to a node), using progressive disclosure to prevent visual clutter.

### Data Inputs & State Subscriptions

* **Subtask Node Topology:** Subscribes to all primary nodes and directed dependency edges (`parent_ids`) for the active `task_id`.


* **Attached Work-Tasks:** Subscribes to child work-items grouped under each Subtask Node, kept collapsed in memory until their parent node is selected.


* **Selected Node Detail Payload:** Reads the active node's `summary`, `inherited_context`, `decision_rationale`, `keychain_ref`, `freshness_tag`, and `exa_sources`.



### Functional Mechanics

* **Progressive Disclosure & Repulsion Layout:**
* By default, only **one** Subtask Node is expanded at a time (defaulting to the currently blocked or most recently active node). All sibling Subtask Nodes render as compact pills showing only title, status indicator, and a collapsed item counter (e.g., `+2 items`).
* **Tap-to-Expand Physics:** When the user taps a collapsed Subtask Node, the previously expanded node collapses its satellite Work-Tasks, the newly tapped node animates toward the focal center, neighboring nodes smoothly shift outward along repulsion vectors to clear space, and the selected node's tethered **Work-Task** satellite chips fan out around it.
* Users can freely drag to pan and pinch (or use `+`/`-` controls) to zoom across large multi-branch task graphs.


* **Two-Tier Bottom Inspector Sheet:**
* **Tier 1 (Immediately Visible Top Summary):** Displays a concise, task-adaptive plain-English synthesis of the selected node's outcome (e.g., selected flight fare and duration for travel, compliance verdict for legal checks, or rating and distance for dining) paired with key metric chips.
* **Tier 2 (Scrollable Deep-Dive):** Scrolling down inside the bottom sheet reveals the full audit trail:
1. *Shared & Inherited Context:* Key-value pills pulled from the `Temporal Memory Store` (`Dates`, `Guests`, `Budget`) and any `vault://` keychain reference used.


2. *Decision Rationale:* Why the winning option was chosen and why competing branches/sources were discarded.
3. *Verified Exa Sources:* Clickable source rows displaying domain favicons, freshness tags (`USED`, `STALE_QUERIED`), and exact Exa highlighted snippets.






* **Actionable Node Shortcuts:** If the user selects a node in `BLOCKED_USER` state, the bottom sheet includes a primary action button (`Resolve Input` or `Open Tab`) that routes directly to the corresponding barrier on **Active Task** or **Keychain Login & Spotlight**.

## 5. Keychain Login and Spotlight (Hidden Tab Reveal)

### Role in the System

**Keychain Login and Spotlight** is the Human-in-the-Loop (HITL) browser escalation surface. When a background `WebView` hits an authentication wall, anti-bot challenge, or final transaction step that cannot or should not be automated autonomously, Laizysink reveals that specific tab, guides the user's eye directly to the required DOM element, and mediates credential autofill without exposing secrets to the AI.

### Data Inputs & State Subscriptions

* **Active Foreground WebView:** Binds the paused `WebView` instance (`tab_id`) to the center viewport.


* **DOM Target Metadata:** Receives the CSS/XPath selector and plain-English instruction tooltip identified by the backend/DOM parser (e.g., `"Sign in to apply your mileage points"`).


* **Keychain Match State:** Queries the local `Zero-Trust Keychain Vault` by matching the `WebView`'s current origin domain (e.g., `jal.co.jp`).



### Functional Mechanics

* **Auto-Scroll & Spotlight DOM Injection:**
* Immediately upon unhiding the `WebView`, the client executes an injected JavaScript payload via `webView.evaluateJavascript(...)`:


1. Locates the target form or button element and calls `element.scrollIntoView({ behavior: 'smooth', block: 'center' })`.


2. Injects a full-viewport backdrop blur/dimming layer (`backdrop-filter: blur(4px)`) while cutting out a sharp, unblurred bounding box around the target element.


3. Anchors a floating instruction tooltip directly above the highlighted element explaining *why* user action is needed.






* **Zero-Trust Biometric Keychain Flow:**
* **Case A — Saved Credential Found:** The bottom sheet displays the matched domain, `vault://` identifier, and masked account preview. Tapping `Autofill with Biometrics` triggers the Android `BiometricPrompt`. Upon fingerprint/face verification, credentials are injected directly into the `WebView` DOM inputs locally; the backend receives only a `KEYCHAIN_REF` event (`vault://jal.co.jp`) and never sees the username or password.


* **Case B — No Saved Credential:** The bottom sheet prompts the user to type credentials directly into the highlighted webpage fields and offers an opt-in toggle (`Save to encrypted Keychain for future tasks`). Once submitted, credentials are encrypted into `Android Keystore` locally.




* **Auto-Re-Hide & Graph Resumption:**
* As soon as the `WebView` detects post-login navigation (URL change or authenticated session cookie) and no further human input is needed, the `WebView` smoothly collapses back into hidden background execution (`alpha = 0f`), strips the spotlight CSS overlay, and returns the user to **Active Task** while the unblocked branch continues.


* Tapping the top-left close/hide control manually backgrounds the tab and pauses that specific branch without canceling sibling branches.

## 6. Completed Task Page

### Role in the System

**Completed Task Page** is the final deliverable and audit ledger for a finished goal. Its role is to prove that every recommendation is grounded in live, verifiable web evidence retrieved via Exa (rather than static LLM training data), show how temporal memory was reused across tasks, and provide a clean handoff to final real-world execution.

### Data Inputs & State Subscriptions

* **Merged Decision Payload:** Reads the root `MERGE` node's final structured output (winning recommendation, pricing/terms, location/timing metadata, and key attributes).


* **Temporal Memory Banner State:** Reads any parent subgraph context injected into this task (e.g., `"Using active trip memory: Japan Trip (Nov 18–23)"`) along with its current freshness status (`Live Synced` / `USED` vs. `STALE_QUERIED`).


* **Verified Citation List:** Subscribes to the merged set of primary Exa sources (`url`, `domain`, `favicon`, `verification_status`, `highlighted_quote`, `retrieved_at`).



### Functional Mechanics

* **Temporal Memory Reuse & Freshness Verification:**
* When a user launches a follow-up prompt (e.g., *"Dinner near my Tokyo hotel"*), the top banner explicitly displays the inherited temporal context (`hotel location`, `trip dates`).


* If any inherited node exceeded its Time-To-Live (TTL) before execution, the system automatically tags it `STALE_QUERIED`, runs a silent Exa refresh before finalizing results, and updates the badge to `Live Verified`. Tapping `Edit` on the banner lets the user override inherited constraints and re-run the merge node.




* **Citation Inspection:**
* Each citation card displays the exact highlighted excerpt extracted by Exa's Contents API alongside its live verification timestamp. Tapping a citation card opens that source URL in an in-app browser preview tab so judges or users can verify the primary source directly.




* **Final Execution Handoff:**
* The primary bottom CTA (e.g., `Open Reservation Tab` or `Open Drafted Reply Email`) transitions control to the human for the final irreversible commitment. If a reservation or checkout page was pre-staged in a hidden `WebView`, tapping the CTA unhides that tab (routing through **Keychain Login & Spotlight** if login or payment confirmation is needed) with dates, party size, and promo codes already populated.




* **Alternative Exploration & Graph Audit:**
* Tapping `Show Other Options` expands runner-up candidates preserved from the `MERGE` node with comparison tradeoffs.


* Tapping the top-right map/graph button opens **Spatial Execution Map** in read-only inspection mode so the user can trace how parallel branches converged on the final answer.
